# Change Proposal: v2-cra-compliance

**Status:** Proposed
**Date:** 2026-05-28
**Author:** Agent

## Summary

Add a CRA (Cyber Resilience Act, Regulation EU 2024/2847) compliance
engine to chainsaw. This is the core differentiator — no existing
open-source tool provides CRA-specific compliance assessment.

## Motivation

### Regulatory Timeline

- **September 11, 2026**: Vulnerability reporting obligations apply
  (Article 14). Manufacturers must report actively exploited
  vulnerabilities to ENISA/CSIRT within 24 hours.
- **December 11, 2027**: All requirements apply. Products must meet
  Annex I essential cybersecurity requirements and carry CE marking.

### What the CRA Actually Requires

The CRA imposes obligations across two dimensions:

**Annex I Part 1 — Product Security Requirements:**
1. Products placed on market without known exploitable vulnerabilities
2. Secure by default configuration
3. Protection against unauthorized access
4. Confidentiality of data (at rest and in transit)
5. Data integrity protection
6. Minimal data processing (data minimization)
7. Availability and resilience
8. Minimal attack surface
9. Incident impact reduction
10. Security-relevant information recording and monitoring

**Annex I Part 2 — Vulnerability Handling Requirements:**
1. Identify and document vulnerabilities and components (SBOM)
2. Address and remediate vulnerabilities without delay
3. Apply effective and regular testing and reviews
4. Publicly disclose fixed vulnerabilities with descriptions
5. Put in place coordinated vulnerability disclosure policy
6. Facilitate vulnerability information sharing
7. Provide mechanisms for secure update distribution
8. Ensure security updates are free and timely

**Article 13 — Manufacturer Obligations:**
- Perform cybersecurity risk assessment
- Integrate cybersecurity into design, development, production
- Exercise due diligence on third-party components
- Document in technical documentation (Annex VII)
- Maintain SBOM covering top-level dependencies

**Article 14 — Reporting Obligations (September 2026!):**
- Early warning to ENISA within 24 hours of awareness
- Vulnerability notification within 72 hours
- Final report within 14 days of corrective measure

**Annex II — User Information:**
- Single point of contact for vulnerability reporting
- Coordinated vulnerability disclosure policy location
- Support period end-date
- Secure update instructions
- SBOM identifier

## Proposed Changes

### New Package: `internal/cra/`

Core compliance assessment engine.

### New Command: `chainsaw comply [path]`

```
chainsaw comply .                              # full CRA assessment
chainsaw comply --report .                     # generate compliance report
chainsaw comply --check article-14 .           # check specific obligation
chainsaw comply --format json|table|html .     # output format
```

### CRA Compliance Checks

#### 1. SBOM Completeness Assessment (`cra/sbom.go`)

Verify SBOM meets CRA Annex I Part 2(1) requirements:

| Check | CRA Reference | Severity |
|---|---|---|
| SBOM exists | Annex I, Part 2, (1) | CRITICAL |
| SBOM format is machine-readable | Annex I, Part 2, (1) | HIGH |
| Top-level dependencies listed | Annex I, Part 2, (1) | HIGH |
| Component versions specified | Annex I, Part 2, (1) | HIGH |
| Component supplier identified | Annex VII | MEDIUM |
| Package URLs (purls) present | Best practice | MEDIUM |
| Integrity hashes present | Best practice | MEDIUM |
| License information present | Annex VII | LOW |
| SBOM freshness (last updated) | Article 13(8) | MEDIUM |

Chainsaw already generates SBOMs — this check verifies they meet
CRA standards, whether generated by chainsaw or another tool
(Syft, Trivy, etc.).

Input: Accept existing CycloneDX or SPDX SBOMs as input, not just
chainsaw-generated ones.

#### 2. Known Vulnerability Assessment (`cra/vulns.go`)

Verify Annex I Part 1(2)(a): "made available without known exploitable
vulnerabilities."

| Check | CRA Reference | Severity |
|---|---|---|
| No known exploitable vulns in deps | Annex I, Part 1, (2)(a) | CRITICAL |
| All known vulns have remediation plan | Annex I, Part 2, (2) | HIGH |
| Security updates available for fixed vulns | Annex I, Part 2, (2) | HIGH |
| Vulnerability fixes applied in timely manner | Annex I, Part 2, (2) | MEDIUM |

This wraps the existing OSV scanning with CRA-specific framing:
instead of "you have 3 HIGH vulns," the output is "Annex I Part 1
non-conformity: 3 known exploitable vulnerabilities remain
unaddressed."

#### 3. Vulnerability Disclosure Process Assessment (`cra/disclosure.go`)

Verify Annex I Part 2(5-6) and Annex II:

| Check | CRA Reference | Severity |
|---|---|---|
| `SECURITY.md` or security policy exists | Annex I, Part 2, (5) | CRITICAL |
| Policy includes disclosure process | Annex I, Part 2, (5) | HIGH |
| Contact information for vuln reporting | Annex II, (8) | HIGH |
| Policy published at documented URL | Annex II, (8) | HIGH |
| `security.txt` (RFC 9116) exists | Best practice | MEDIUM |
| PGP/GPG key for encrypted reporting | Best practice | LOW |

Implementation: parse `SECURITY.md`, `.github/SECURITY.md`, and
`security.txt` (well-known URI format). Check for required elements:
- Contact email or URL
- Disclosure timeline
- Scope definition
- Safe harbor language

#### 4. Update Mechanism Assessment (`cra/updates.go`)

Verify Annex I Part 2(7) and Part 1(2)(c):

| Check | CRA Reference | Severity |
|---|---|---|
| Release mechanism exists (tags, releases) | Annex I, Part 2, (7) | HIGH |
| Security updates separable from feature updates | Annex I, Part 2, (2) | MEDIUM |
| Changelog documents security fixes | Annex I, Part 2, (4) | MEDIUM |
| Automatic update mechanism documented | Annex I, Part 1, (2)(c) | LOW |

Implementation: check for `CHANGELOG.md`, GitHub releases, git tags
matching semver patterns. Parse changelog for security-related entries.

#### 5. Support Period Assessment (`cra/support.go`)

Verify Annex II(6-7):

| Check | CRA Reference | Severity |
|---|---|---|
| Support period end-date documented | Annex II, (7) | HIGH |
| Support period >= 5 years or product lifetime | Article 13(8) | MEDIUM |
| EOL/deprecation notice present | Best practice | LOW |

Implementation: look for support period declarations in README,
package metadata, or dedicated support policy files.

#### 6. Article 14 Reporting Readiness (`cra/reporting.go`)

**This is the most time-sensitive check — obligations apply September
2026.**

| Check | CRA Reference | Severity |
|---|---|---|
| Vulnerability monitoring in place (CI scan) | Article 14 prerequisite | CRITICAL |
| CSIRT contact point identified | Article 14(2) | HIGH |
| Internal process for 24h early warning | Article 14(2)(a) | HIGH |
| Internal process for 72h notification | Article 14(2)(b) | HIGH |
| Template for final report (14 days) | Article 14(2)(c) | MEDIUM |

Implementation: check for CI/CD scanning configuration (GitHub Actions
workflows calling security scanners), documented incident response
procedures, CSIRT/ENISA contact configuration.

This check is partially heuristic — it verifies that observable
artifacts suggest readiness, not that internal processes actually exist.
The output is a readiness checklist, not a certification.

### Compliance Report Format

New output format for `chainsaw comply --report`:

```
CRA Compliance Assessment — 2026-05-28
Product: myproduct v2.1.0
Assessment tool: chainsaw v0.2.0

OVERALL STATUS: PARTIAL COMPLIANCE (67%)

ANNEX I PART 1 — PRODUCT SECURITY
  [PASS]  (2)(a) No known exploitable vulnerabilities
  [FAIL]  (2)(b) Secure by default — not assessable via static analysis
  [N/A]   (2)(c) Automatic updates — not applicable (library)

ANNEX I PART 2 — VULNERABILITY HANDLING
  [PASS]  (1) SBOM — CycloneDX 1.5, 142 components, top-level deps covered
  [WARN]  (2) Remediation — 2 dependencies have available patches not applied
  [PASS]  (5) Coordinated disclosure — SECURITY.md present with process
  [FAIL]  (6) Contact information — no security.txt or contact email

ARTICLE 14 — REPORTING READINESS (effective Sept 2026)
  [PASS]  Vulnerability monitoring — osv-scanner in CI pipeline
  [FAIL]  CSIRT contact — not configured
  [FAIL]  24h early warning process — not documented
  [WARN]  72h notification template — partial

ANNEX II — USER INFORMATION
  [PASS]  (8) Vulnerability reporting contact
  [FAIL]  (7) Support period end-date — not documented

RECOMMENDATIONS:
  1. [CRITICAL] Configure CSIRT contact for Article 14 reporting
  2. [CRITICAL] Document 24h early warning process before Sept 2026
  3. [HIGH] Apply available patches for 2 vulnerable dependencies
  4. [HIGH] Add support period end-date to README/package metadata
  5. [MEDIUM] Add security.txt (RFC 9116) to well-known URI
```

### Policy Integration

Extend `.chainsaw.yaml` for CRA configuration:

```yaml
cra:
  # Product identification
  product-name: "My Product"
  product-version: "2.1.0"
  manufacturer: "My Company GmbH"

  # Support period (Annex II)
  support-end-date: "2031-12-31"

  # CSIRT for Article 14 reporting
  csirt-contact: "https://www.bsi.bund.de/csirt"
  enisa-reporting-url: "https://vulnerability.enisa.europa.eu"

  # Vulnerability disclosure
  security-contact: "security@mycompany.eu"
  disclosure-policy-url: "https://mycompany.eu/.well-known/security.txt"

  # Conformity assessment (Article 24)
  product-category: "default"  # or "class-i", "class-ii"
  assessment-type: "self"      # or "third-party"
```

### SBOM Import

New flag for consuming third-party SBOMs:

```
chainsaw comply --sbom existing-sbom.json .
chainsaw comply --sbom spdx-sbom.spdx .
```

Parse CycloneDX (JSON/XML) and SPDX (JSON/tag-value) SBOMs generated
by other tools (Syft, Trivy, etc.) and assess against CRA requirements.

## Dependencies

- No new external dependencies. SBOM parsing uses `encoding/json` and
  `encoding/xml` from stdlib.
- SPDX parsing uses tag-value line parser (stdlib).

## Non-goals

- Replacing legal counsel. Chainsaw assesses technical artifacts, not
  legal compliance. Output explicitly states this.
- Conformity assessment certification. Chainsaw is a readiness tool,
  not a notified body.
- Annex I Part 1 security properties assessment (secure by default,
  access control, cryptography). These require runtime analysis or
  manual review, not static scanning.
- Full Annex VII technical documentation generation. Chainsaw checks
  for artifacts; it does not generate legal documentation.

## Risks

- CRA implementing acts and harmonised standards are still being
  developed. Chainsaw's checks may need updating as standards are
  published. Mitigation: structure checks as configurable rules, not
  hardcoded logic.
- Compliance assessment is inherently subjective in some areas (e.g.,
  "without known exploitable vulnerabilities" requires context about
  exploitability). Mitigation: be conservative, flag for review,
  never claim full compliance.
- Organizations may over-rely on tool output for legal compliance.
  Mitigation: every report includes a disclaimer that this is a
  technical assessment aid, not legal advice.

## Acceptance Criteria

- `chainsaw comply .` produces a CRA compliance assessment
- Checks cover Annex I Part 2, Article 14, and Annex II requirements
- Accepts existing CycloneDX and SPDX SBOMs as input
- JSON output suitable for GRC tool integration
- `.chainsaw.yaml` accepts CRA-specific configuration
- Report clearly states it is a technical assessment, not certification
- Article 14 readiness checks highlight the September 2026 deadline
